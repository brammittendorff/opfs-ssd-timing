FROST PoC - SSD contention from JavaScript via OPFS

Times random 4 kB reads on a large OPFS file. When something else touches the same SSD, read latency spikes. Local research use only.

Three channels - three shared resources you can time (pick one in the Channel dropdown). They sense different things and some are browser-dependent:
1. read - senses DISK activity. Grows an OPFS file until random 4 kB reads stop being served from RAM and start hitting the SSD, then times those reads. The paper's method; strongest of the three (a competing disk write collapses its read throughput). Works in Chrome and Firefox, but needs the OPFS quota to exceed free RAM - otherwise the file stays cached and there is no knee (Firefox caps the quota at ~10 GB).
2. cache-occupancy - senses CPU / memory / WEBSITE activity (a different resource: the CPU's last-level cache). No file at all: it sweeps a buffer ~the size of your LLC as a randomized pointer-chase and times the sweep; when anything else touches the cache, the sweep slows. Leave auto-size checked and it finds your LLC for you. The median sweep time is the signal here. Works in Chrome and Firefox, zero setup - the portable default for sensing apps/sites.
3. write-flush - senses DISK writeback, but only on browsers where flush() really fsyncs. Writes 4 kB and times handle.flush(). Works in Firefox (flush forces a real ~hundreds-of-us writeback, so it detects disk writes with no big file needed). On Chrome it does NOT work - Chrome's flush() is a no-op (~5 us, no fsync), so it senses no disk. Use it on Firefox when the quota is too small for the read channel.

In short: for disk events use read (any browser) or write-flush (Firefox); for CPU / memory / websites use cache-occupancy (any browser).

Mitigation (from the paper): capping OPFS to ~1 GB makes the file fit in RAM, so reads stay cache-served and the read channel disappears. All channels need crossOriginIsolated for the high-res timer (set via COOP/COEP in serve.py); opening the HTML as a file:// will not work.
